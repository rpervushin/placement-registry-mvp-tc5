# Задачи по развёртыванию сервиса

Краткий перечень задач по этапам (детали — в `ARCHITECTURE.md`).

## MVP

1. Завести репозиторий в корп. GitLab, настроить CI (lint/test) по образцу MS Catalog.
2. Поднять скелет FastAPI-сервиса (routers/services/domain_services/repositories/settings) +
   Dockerfile на корп. базовом образе.
3. Поднять PostgreSQL + Alembic-миграции под доменную модель (Placement, DiscoveryEvent, AuditLog).
4. Подключить Redis (`cashews`) для кэша конфигурации на чтение.
5. Реализовать `admin`-API: просмотр и правка конфигурации плейсментов (Read+Update; без
   Create/Delete — плейсменты появляются автоматически через discovery), карта плейсментов.
6. Реализовать `internal`-эндпоинт приёма push от RecSys (входящие данные: новый `placement_id`,
   метаданные, по расписанию/триггеру) — без исходящего HTTP-клиента к RecSys.
7. Подключить X5ID-аутентификацию (без ролевой модели — только Администратор реестра).
8. Подключить observability (`x5d-monitoring`: логи, APM, Prometheus, health-checks); опционально —
   мониторинг запросов от Catalog.
9. Реализовать `arq`-воркер для discovery-событий (обнаружение неактивированных точек).
10. Собрать Admin UI (React): просмотр конфигурации, карта полок.
11. Получить k8s/Helm-манифесты у платформенной команды, выкатить в тестовый контур.
12. Пройти архитектурное согласование (арх. комитет).
13. Получить оценку backend по зафиксированному API-контракту и схеме Postgres; ориентир со
    стороны RecSys на их часть — 3–4 дня разработки + ~2 дня тесты/публикация на интеграционной
    платформе.
14. Зафиксировать решение по плейсментам поиска/листинга RecSys (4–6 шт., хардкод в коде
    RecProcessing, не в БД) — предварительно: не включаем в реестр на MVP/Этапе 2, вернуться
    после перехода RecProcessing с Python на Go.

## Этап 2 — дополнительные источники

1. Подключить клиент Catalog как полноценный источник (плейсменты, категории/товары).
2. Реализовать клиент X5 Media (новый источник плейсментов).
3. Подключить синхронизацию `ab_status` с AB-платформой (`arq`-воркер по расписанию).
4. Добавить роль «Владелец полки» и разграничение доступа по владельцам полок.
5. Подключить Kafka (`aiokafka`/Faust) для event-driven инвалидации кэша и discovery в реальном
   времени.
6. Расширить Admin UI под управление несколькими источниками и владельцами.

## Перспектива (не прорабатываем сейчас)

- Передача в реестр управления приоритетами и кросс-полочными правилами (оркестратор).
