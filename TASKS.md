# Задачи по развёртыванию сервиса

Краткий перечень задач по этапам (детали — в `ARCHITECTURE.md`). Порядок в MVP —
последовательный: согласование архитектуры идёт до старта разработки, а не параллельно с ней.

## MVP

**Согласование (до старта разработки)**

1. Показать идею и сервис команде Рекомендаций Каталога — деливери Анастасия Силуанова,
   Владимир Мальцев.
2. Обсудить с лидом разработки Антоном: верхнеуровневый анализ, валидация архитектуры и
   C4-диаграмм.
3. Пройти архитектурное согласование (арх. комитет, грумминги).

**Инфраструктура (может идти параллельно с согласованием)**

4. DevOps: подготовить инфраструктуру для развёртывания (k8s/Helm-манифесты, тестовый контур).
5. Завести репозиторий в корп. GitLab, настроить CI (lint/test) по образцу MS Catalog.

**Разработка**

6. Поднять скелет FastAPI-сервиса (routers/services/domain_services/repositories/settings) +
   Dockerfile на корп. базовом образе — пустой сервис.
7. Поднять PostgreSQL + Alembic-миграции под доменную модель (Placement, AuditLog).
8. Реализовать `internal`-эндпоинт приёма push от RecSys: входящий список актуальных
   плейсментов и их настроек, по расписанию/триггеру. Обработка — синхронно в хендлере
   (см. примечание про `arq` ниже), без исходящего HTTP-клиента к RecSys.
9. Реализовать `admin`-API: просмотр и правка конфигурации плейсментов (Read+Update; без
   Create/Delete — плейсменты появляются автоматически через push от RecSys), карта плейсментов.
10. Подключить read-only датасорс к Grafana/Prometheus: метрики по `placement_id` ручки
    `/context` Каталога (RPS, p95 latency, error rate, last_request) — без изменений на стороне
    Catalog. Детали и открытые вопросы (label для `placement_id` в метриках, готовый дашборд) —
    `prototypes/integration-requirements.html`. Сначала ресёрч: готовый виджет/библиотека
    Grafana или собственная отрисовка.
11. Подключить X5ID-аутентификацию (без ролевой модели — только Администратор реестра).
12. Подключить observability (`x5d-monitoring`: логи, APM, Prometheus, health-checks).
13. Собрать Admin UI (React): конфигурация плейсмента рядом с его метриками из Grafana, карта
    полок.

**Открытое / для уточнения**

14. Зафиксировать решение по плейсментам поиска/листинга RecSys (4–6 шт., хардкод в коде
    RecProcessing, не в БД) — решение пока открыто, не берём в работу до перехода RecProcessing
    с Python на Go.

> **`arq`-воркер на MVP не нужен.** Раньше планировался для discovery-событий (автообнаружение
> неактивированных `placement_id` в трафике), но RecSys и так присылает полный список своих
> актуальных плейсментов через push (п. 8) — отдельный механизм обнаружения избыточен. `arq`
> возвращается на Этапе 2, когда понадобится периодический опрос AB-платформы (там push нет).

### Оценка (по итогам встречи с лидом бэкенда Каталога, предварительная — до решения о взятии в работу и выделения ресурсов)

| Этап | Содержание | Дни |
|---|---|---|
| Анализ | архитектура, согласование артефактов, грумминги (пп. 1–3) | 5–7 |
| Инфраструктура | работа DevOps по развёртыванию (п. 4) | 2 |
| Сервис (скелет) | разработка и размещение пустого сервиса (п. 6) | 7 |
| Эндпоинт RecSys | приёмная ручка для push-данных (п. 8) | 5–7 |
| Grafana | ресёрч интеграции (п. 10) | 2 |
| Admin UI | React-админка (п. 13) | 5 |
| **Итого** | | **26–30** |

Сумма последовательных оценок; часть этапов (например, анализ и подготовка инфраструктуры)
может идти параллельно, так что календарный срок может быть короче. Отдельно: ориентир со
стороны самого RecSys на реализацию push на их стороне — 3–4 дня разработки + ~2 дня
тесты/публикация на интеграционной платформе (это другая команда и другой объём работ, не
входит в таблицу выше).

## Этап 2 — дополнительные источники

1. Подключить клиент Catalog как полноценный источник (плейсменты, категории/товары).
2. Реализовать клиент X5 Media (новый источник плейсментов).
3. Подключить синхронизацию `ab_status` с AB-платформой (`arq`-воркер по расписанию).
4. Добавить роль «Владелец полки» и разграничение доступа по владельцам полок.
5. Подключить Kafka (`aiokafka`/Faust) для event-driven инвалидации кэша и discovery в реальном
   времени.
6. Расширить Admin UI под управление несколькими источниками и владельцами.

## Перспектива (не прорабатываем сейчас)

- Передача в реестр управления приоритетами и кросс-полочными правилами (оркестратор).
